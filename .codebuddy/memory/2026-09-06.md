## 续21: 未点击标记格却弹出「明细表N 设计」弹框（尤其选整行/行号）
**现象**: 没点明细表标记格也弹明细设置 Modal（`editingDetail!==null`）；尤其点行号选中整行必弹。
**根因**: 主画布 `onSelectionChange` 处理里，只要选区首格坐标命中 `cellFieldMetaMap` 的 `detailTableMarker` 就 `onDetailMarkerOpen(idx)` 打开弹框。
选整行（点行号）是跨列范围选区，其首格被解析为 `(行, 起始列)`；若此前该行激活列恰为标记列（Univer 保留锚点），`(行,标记列)` 命中标记 → 误弹。
**修复**(UniverExcelGrid.tsx, onSelectionChange 处理):
1. 计算 `isSingleCell = startRow===endRow && startCol===endCol`；仅单格选区才允许打开明细画布，整行/整列范围选区不打开。
2. 加载布局期间（`isLoadingRef.current`）不选区触发打开，避免 loadLayoutData 还原定位到标记格时误弹。
3. 仍保留：直接单击标记格（单格）→ 正常打开；其余选区照常广播 `univer-cell-selected` 供属性面板。
**验证**: lint 0 错误。待用户停 dev server 重启+硬刷新验证：点行号选整行不再弹框；单击标记格仍打开明细画布。

## 续22: 插入/删除行或列后字段与字段名错位且"多出"
**现象**: 字段+字段名排好后，在单元格上插入行/列，字段和字段名错位，且多出（面板可重复拖入）。
**根因**: `handleRowColStructural` 平移 `cellFieldMetaMap` 键时对**所有**存活字段统一加减 `delta`，
而 Univer 只在「变更点之后」的单元格才移动内容。结果：插入点之上的字段 Map 坐标整体 +count 但内容未动 → Map 与表格真实内容错位；
错位后上方字段 `getCellFieldMeta` 取不到 meta → 保存时丢失、面板置灰被释放 → 可重复拖入（"多出"）。
**修复**: 改为仅平移「变更点之后」的字段——插入(delta=+count): `pos>=start` 才平移；删除(delta=-count): `pos>end` 才平移（pos<start 不动，落在区间内的已被 doomed 移除）。
这样 Map 与 Univer 实际移动的内容一致，错位+"多出"同时消除。行列共用同一 `pos` 判定。
**验证**: lint 0 错误。逻辑与 Univer 插入/删除单元格行为对齐；待用户实测：插入/删除行列后字段+字段名位置正确、无多余可拖入项。

## 续23: 删除行/列仍错位+"多出"（与插入同源，更深一层）
**现象**: 插入行列修好后，删除行/列依然字段/字段名错位且"多出"。
**根因（核心）**: Univer 删除/插入行或列时，内部会用 `move-range` 把整块内容上/下/左/右平移来压缩/腾位。
于是 `onCommandExecuted` 里 `remove-row/insert-row`(→`handleRowColStructural`) 与 `move-range`(→`handleMoveRange`)
对「同一动作」各自平移 `cellFieldMetaMap` 一次 → **双重平移** → 字段被移两次 → 错位 + 多出。
插入只走 remove/insert 命令、不触发内部 move-range，所以续22 把插入修好、删除仍坏——正好对上现象。
**修复**: `handleMoveRange` 增加判定：当移动是「整行宽(列0→末列)的纵向平移」或「整列高(行0→末行)的横向平移」时，
判定为结构性行/列变更并 `return`，改由 `handleRowColStructural` 统一平移，杜绝双重平移。
普通用户拖拽（局部范围）仍正常处理。配合续22 的「仅平移变更点之后字段」，删除对齐与"多出"同时消除。
**验证**: lint 0 错误。待用户实测：删除行/列后字段+字段名位置正确、无多余可拖入项。

## 续24: 行列操作仍错位+多出（终极根因：陈旧闭包 + 守护反还原）
**实测日志证据**: 右键行列操作后抛 `UniverExcelGrid.tsx:1704 TypeError: Cannot read properties of null (reading 'getActiveSheet')`，
随后 `[Prune] 清理孤儿字段: 2_0/2_1`、`[Guard] 自动还原: ['3_1']`。
**根因（两层）**:
1. `handleRowColStructural` 用了闭包里的 `workbook`（注册 `onCommandExecuted` 时首帧 `workbook=null` 被捕获）→ 调 `(null).getActiveSheet` 抛异常，
   **平移逻辑整段没执行**；Univer 已移动内容而 Map 没动 → 错位。别处(`findMetaNear` 等)都用 `workbookRef.current`，唯独这里用 `workbook`。
2. 守护定时器(800ms)扫描发现"位移后的格值 ≠ 其旧坐标 meta 期望值" → 当成手动改格自动还原 → 抵消/加剧错位。
**修复**:
- `handleRowColStructural`/`handleMoveRange`/`saveLayoutData` 全部改用 `workbookRef.current`（ref 始终指向真实实例，杜绝陈旧闭包）。
- 新增 `isStructuralRef`：结构性行/列操作期间置位，让 `onCommandExecuted` 单元格变更处理器(2608)与守护定时器(2728)跳过，
  不把合法位移当篡改还原。
- 配合续22(仅平移变更点之后字段)+续23(move-range 全幅平移跳过，防双重平移)。
**结论**: 行列插入/删除 = remove/insert 命令(handleRowColStructural 平移) + 内部 move-range(全幅, 跳过) 同一动作，现已单一定位、用 ref、并被守护跳过。
**验证**: lint 0 错误。待用户停 dev server 重启+硬刷新实测：单元格上新增/删除行列后字段与字段名对齐、无多出。

## 续25: 行列操作后错位+多出（终极根因：自保存触发的整表重载死循环）
**实测日志**: 右键 row1 插入行后 Map 已正确平移为 ['2_2','3_2','4_2','5_2']，但紧接着反复出现
`[Layout] layoutData 变化，重新加载` → `[Prune] 清理孤儿 6_2` → `广播已放置字段=(2) detail labels` → `Map 4→3→4→3` 振荡，主表字段被清空/丢失。
**根因**: `useEffect` 监听 `layoutData` 变化会整表 `loadLayoutData` 重载。原有防回流 guard 用
`selfSavedLayoutsRef.current.has(layoutData)` 做**引用比较**；但父组件 `ExcelDesign.handleLayoutChange`
(`setLayoutData((prev)=>({...data, detailTables: prev.detailTables||{}}))`) 把自保存的 `data` 包成**新对象**(新引用+注入 detailTables)，
引用不等 → guard 失效 → 每次自保存都触发整表重载 → 重载清单元格又触发保存 → **死循环**，主表字段在振荡中被反复清空/"多出"。
**修复**: 把引用比较改为**内容签名比较**(新增模块级 `stableStringify` 递归排序key + `stripDetailTables` 剔除父组件注入的 detailTables)。
自保存时在 `saveLayoutData` 两分支写入 `selfSavedSigRef.current = stableStringify(parentData)`；
effect 中 `incomingSig = stableStringify(stripDetailTables(layoutData))`，若与 `selfSavedSigRef` 相等则**跳过 reload**。
这样自保存的回流变化被精确识别、不再重载；外部变化(loadFormLayout/切换记录)签名不匹配仍正常重载。
**副作用解决**: 重载死循环消失 → 不再清字段/不再振荡 → 错位+"多出"消除。Map 在 handleRowColStructural 中已正确平移(续22/23/24)，重载跳过即保留正确态。
**注意**: 快照显示原布局里 `field_9` 同时出现在 1_2 与 2_2(重复放置，疑似早期坏操作遗留的数据重复)，本修复只防"新增"重复，旧重复需另清。
**验证**: lint 0 错误。待用户停 dev server 重启+硬刷新实测：单元格上新增/删除行列后字段与字段名对齐、无多出、无振荡丢失。

## 续26: 增加行/列后"下面的单元格把其他字段覆盖掉"（双重平移 + 破坏性还原 + 自愈）
**现象**: 右键 row0 插入行后，日志显示 Map 已正确平移，但 [Save] 里反复：
`单元格 (2,1) 值不匹配，还原为期望值: 实际值="📝 ${field_10}", 期望值="🔒 📝 ${field_9}"`
即把 (2,1) 里 field_10 的内容**强行覆盖成 field_9** → 用户看到"覆盖/多出"。
**根因(两层)**:
1. **meta 比内容多移一行 = 双重平移**。插入行时 Univer 内部派发整幅 move-range 把内容上/下平移，
   `handleMoveRange` 的跳过判定要求移动覆盖"整张表全部列"(`fC1 >= maxCols-1`)，但字段只占 0~1 列、
   表的 maxCols 很大 → 跳过不成立 → `handleMoveRange` 又平移了一次地图 → 与 `handleRowColStructural` 叠加。
   （日志里 Map 在插入前就已比内容多一行，是历史双重平移累积的偏移；插入只是把两边都 +1、保留偏移。）
2. **保存的"值不匹配→还原期望值"是破坏性的**。当某 meta 坐标处实际是"别的字段"占位符时，它把
   当前格内容 setValue 成 meta 期望值 → 直接覆盖掉别的字段（这就是"覆盖"的可见表现）。
**修复**:
- `handleMoveRange` 顶部加 `if (isStructuralRef.current) return;`（结构性操作期间整体跳过，交给 handleRowColStructural 统一平移），杜绝未来再双重平移。
- `saveLayoutData` 保存自愈：主循环遇到"当前格是别的字段占位符"(cellName≠metaName)时**不覆盖**，记入 `pendingRehome`；
  循环结束后用 `fieldNameIndex`(字段名→实际坐标，扫描时建立)把错位 meta 搬回它自己字段内容所在坐标（防碰撞：先删全部 source 再放 home），
  找不到本字段内容才 `markFieldRemoved` 释放；最后用自愈后的地图把正确 `fieldMeta` 重新同步进 `cellData`。
  新增模块级 `extractFieldNameFromDisplay(v)` 取 `${...}` 内字段名。同字段(仅图标差异)/纯文本占位符仍走原还原逻辑（非破坏性场景不变）。
**效果**: 插入行不再制造新偏移；既有偏移在下次保存时被自愈搬正，且绝不再把别的字段内容覆盖掉。
**验证**: lint 0 错误。待用户停 dev server 重启+硬刷新实测：插入/删除行列后字段与字段名对齐、不再覆盖/多出。

## 续27: 续26 修后仍"覆盖+多出"——破坏性还原还有两处（实时轮询 + 值变更处理器）
**现象(用户反馈)**: 续26 改了 saveLayoutData 自愈，但单元格上插入/删除行列、多字段/字段名时仍被覆盖、多出。
**根因补充**: 续26 只修了「保存时」，但还有两处**实时**破坏性还原比保存自愈更早发生：
1. **实时防篡改轮询** `setInterval(…,800)`（原 2920 行）：每轮对 meta 所在格 `!isCellValueMatchMeta` 就 `setValue(getCellDisplayValue(meta))` 强行写回期望值 → 把被平移过来的「别的字段」内容覆盖掉（可见"覆盖"），且错位 meta 使同一字段出现在两处（"多出"）。
2. **`set-range-values` 值变更处理器**（原 2866 行）：Univer 插入内部写值触发该事件，若此刻 meta 错位，也把"别的字段"强行还原成期望值 → 插入过程中即覆盖。
   - 注：双重平移（handleRowColStructural + handleMoveRange 都平移）有可能让同一字段落到两个坐标 → "多出"；内容侧 Univer 只平移一次不会重复。
**最终方案 = 内容驱动自愈（不依赖命令顺序/标志位预测）**：
- 新增 `reconcileMetaWithContent(sheet)`（定义在 pruneOrphanFieldMeta 之后）：扫描全表按 `${字段名}` 建 `fieldContentIndex`，把每个 meta 搬回其字段内容真实坐标（字段格直接搬；标签格随字段内容左移一格搬）；找不到内容时：当前格是别的字段→整字段释放(陈旧孤儿)，当前格空/普通文本→整字段移除/还原占位符。绝不覆盖别的字段。
- **实时轮询改造**：去掉 destructive `setValue` 覆盖。先轻量预检 meta 格（空或字段值不匹配）判 `needReconcile`，命中才调 `reconcileMetaWithContent` 全表扫描自愈；并 `notifyFieldsChanged`+`scheduleAutoSave`。`pruneOrphanFieldMeta` 在轮询中不再单独调用（reconcile 已涵盖移除语义，且避免把"被平移走"的空格误删）。
- **值变更处理器改造**：空值清除分支在 `isStructuralRef` 期间 `return`；篡改还原分支在 `isStructuralRef` 期间跳过，且当 `extractFieldNameFromDisplay(newValue)` 是「别的字段」时 `return`（交给 reconcile 自愈），仅保留"同字段图标差异/纯文本被改"的还原。
- `handleMoveRange` 仍保留 `isStructuralRef` 守卫（best-effort 防双重平移）；`saveLayoutData` 的 pendingRehome 自愈保留（保存层面兜底）。
**效果**: 任何顺序的平移/双重平移 → 地图在 800ms 内自愈到与内容一致；插入/删除行列不再覆盖别的字段、不再多出。
**注意**: `reconcileMetaWithContent` 引用了后定义的 `removeFieldCompletely`，故**不列入其 useCallback deps**（闭包前向引用在调用时才求值，已验证 lint 0 错；若列入 deps 会因 TDZ 渲染崩溃）。
**验证**: lint 0 错误。待用户停 dev server 重启+硬刷新实测：单元格上插入/删除行或列，多字段/字段名均对齐、无覆盖、无多出。

## 续28: 新增行列后做「只读/可编辑/必填」属性操作 → 原字段被最新字段覆盖
**现象**: 行列移动后字段位置已正确，但右键做字段属性(只读/可编辑/必填)时，被操作的字段格会被「最新的字段」覆盖。
**根因**: `setFieldAttr(row,col,attr)` 开头有一段「从持久化布局补全」逻辑：用 `layoutDataRef.current`(=已保存、插入前的旧布局) 的 `r,c` 直接 `cellFieldMetaMap.current[`${r}_${Number(ck)}`] = fm`。新增行列后旧布局坐标仍是插入前位置 → 把 Map 用旧坐标覆盖回去；随后 `Object.entries(map)` 遍历这些过期坐标 `setValue` → 正好写进被平移过来的其它字段格 → 表现为「原字段被最新字段覆盖」。
**修复 = 内容驱动写回**（与 reconcile 同一思想）：
- 去掉「旧布局坐标覆盖 Map」那段；只从 Map/布局取**字段定义**(fieldId/fieldName) 作 baseMeta。
- 先按 `fieldId` 清空 Map 中该字段所有旧条目（含过期坐标）。
- 用 `extractFieldNameFromDisplay` 扫描表格当前内容，定位该 `${fieldName}` 真实所在的字段格；标签格从其左侧一格(非 `${`) 重新登记，但不覆盖标签文字。
- 仅对这些**当前真实坐标** `setValue(getCellDisplayValue)`+`applyFieldAttrStyle`，包裹 `isRestoringRef` 防递归；末 `notifyFieldsChanged`+`saveLayoutData`。
**效果**: 属性操作始终写回字段真实当前位置，不再错格覆盖其它字段。
**注意**: `resolveCellFieldId(row,col)` 仍用于拿 fieldId→字段定义；只要 reconcile 已对齐 Map（800ms内）其解析即正确。写回坐标现已完全不依赖 Map key / 旧布局。
**验证**: lint 0 错误。待用户停 dev server 重启+硬刷新实测：新增行列后，对各字段分别做只读/可编辑/必填，互不覆盖。

## 续29: 续28 改后"先删旧条目再按内容扫描重填"→ 标签项漏登记，面板字段名由灰变黑
**现象**: 新增行列后不覆盖了，但做属性操作时(a)状态错位(b)面板部分字段/字段名由灰变黑(变可拖)。
**根因**: 续28 的 `setFieldAttr` 用 `delete` 清掉该 fieldId 全部 Map 条目，再以「扫描表格内容」重填。
标签项仅在「左侧一格是标签文字」时才重登记 `${fieldId}_label`；若标签非紧贴左侧或独立放置，`${fieldId}_label` 缺失
→ FieldPalette 标签项 `disabled={labelUsed=false}` → 由灰(#bfbfbf)变黑(#262626)。扫描漏掉则字段项也黑。
**修复 = 保留已对齐 Map，不再删后扫**（回归最小安全实现）：
1. 去掉「旧布局坐标覆盖 Map」与「先删后扫」两段危险逻辑。
2. 仅从 Map/布局取字段定义 baseMeta，更新 fieldAttr/required/readonly。
3. 写回前主动调 `reconcileMetaWithContent()` 一次，确保 Map 键已对齐字段真实当前位置（即便 800ms 守护未触发）。
4. 遍历 Map 中该 fieldId 的全部条目（标签+字段，坐标即当前真实位置），`setValue(getCellDisplayValue)`+`applyFieldAttrStyle` 写回；
   Map 为空(极端重载未填充)才退回按布局坐标写回。
5. 包裹 `isRestoringRef` 防递归；末 `notifyFieldsChanged`+`saveLayoutData`+派发 `univer-field-attr-applied`。
**效果**: 不删任何 Map 条目→usedFieldKeys 恒定→面板标签/字段项保持置灰；按对齐后的真实坐标写回→不覆盖、状态不错位。
**关键教训**: 字段属性写回「绝不能用会丢失/重排 Map 条目的方式」；Map 是面板置灰唯一事实源，删条目=字段变黑。写回坐标以 reconcile 对齐后的 Map 为准。
**验证**: lint 0 错误。待用户停 dev server 重启+硬刷新实测：新增行列后，对各字段/字段名分别做只读/可编辑/必填，互不覆盖、状态正确、面板标签与字段项均保持置灰不回黑。

## 续30: 续29 仍"状态错位+字段被覆盖+面板灰变黑"——三项根治
**实测归因（用户确认"灰变黑是新增行列造成的"）**:
1. **setFieldAttr 仍错位/覆盖**: 续29 写回前调 `reconcileMetaWithContent()` **漏传 sheet** → 该函数 `if(!sheet) return false` 是**空操作**，Map 从未对齐；且 `resolveCellFieldId(row,col)` 在 reconcile 前用**陈旧 Map 坐标**解析 fieldId → 点到 A 却拿到 B 的 fieldId，写回时把属性套到错格、覆盖别的字段。
2. **面板灰变黑（核心根因）**: `reconcileMetaWithContent` 与 `rebuildFieldMetaFromSheet` 的扫描上限为 `maxCol=min(getMaxColumns,50)`。新增列把字段推到列索引 `==50` 时落在 `[0,50)` 之外 → 占位符扫不到 → `home` 为空 → `!home` 分支 `removeFieldCompletely` → 字段从 Map 移除 → 面板灰变黑。若 `handleRowColStructural` 因命令 id 未匹配未平移 Map，旧坐标格变空更会触发此删除。

## 续33: 环依赖升级——不只是 getActiveSheet，任何 facade 解析都成环（FRange / FSelection）
**新报错**:
1. `[Save] 读取单元格 (100,25) 失败… identifier "FRange"` @ `saveLayoutData` 的 `sheet.getRange`，栈 `onCommandExecuted(2830)→handleRowColStructural(2036)→saveLayoutData(1580)`；后果严重：整表 getRange 全被跳过 → **写入空布局、把布局清空**。

**根因升级（重要认知修正）**:

**修复（架构级：命令执行中不做 facade，一律延迟）**:
1. 命令执行中触发的 `saveLayoutData()` 全部 `setTimeout(…,0)`（removeField / RowColStructural / MoveRange / CellChange / clearCell 五处）。
2. `clearCell` 的 `getActiveSheet()`→`sheetRef.current`；`getSelection()` 两处（handleFieldAttrChange、getSelection helper）包裹 try/catch，失败回退 `rightClickCellRef`。

**⚠️ FIFO 时序陷阱（易错点，务必记住）**: `isStructuralRef` 必须**同步置位**（供紧随的 set-range-values 判定"平移中"），但**复位不能在同步段排队**——macrotask FIFO 会让"复位"排在"结构性处理(B)"与"set-range-values 处理(C)"**之前**执行，导致平移出的空格被误判为清空而删字段。正确做法：复位放在**延迟后的结构性分支末尾**再 `setTimeout(...,0)`，保证顺序为 B→C→复位。

## 续37: 「反复弹布局数据加载成功 + 增删行/列后面板灰变黑 + 属性不生效」——保存双形状回调导致重载死循环

**根因A（重载死循环，主因，②③ 是它的连带后果）**: `saveLayoutData` **以两种不同形状回调两次**：
- 内部 `onLayoutChange(parentData)`（1952/1962），`parentData = { [sheetName]: result, sheetName, cellData, rowCount, colCount, version, spreadCompat }`；
- 函数 `return result`（1963），而多数调用方（2239/2452/2883）拿到返回值后**再以 `result` 回调一次并覆盖 layoutData**，`result = { id, sheetOrder, sheets, sheetName, spreadCompat }`。
两者形状完全不同。但 `selfSavedSigRef` 只记了 **parentData** 的签名 → 重载 effect 里 `incomingSig`（实际是 result 形状）**永远不匹配** → **每次保存都触发整表重载 → 反复弹 toast**；而每次重载又用快照清空并重建 `cellFieldMetaMap` → ②面板灰变黑、③属性失效。
**修复A**: 新增 `selfSavedSigAltRef` 记录 `result` 形状签名（空布局分支同步赋值），重载判定改为**命中任一签名即跳过**（`selfSavedHit`）。
**根因B（续34 引入的回归）**: 续34 把 `onCommandExecuted` 整个处理体包进 `setTimeout(0)`，但**守卫标志仍在延迟体里现取**。而 `isLoadingRef` 在 `loadLayoutData` 的 `finally`(1561) 已被复位、`isPlacingFieldRef/isRestoringRef` 同理 → 延迟体执行时守卫为 false → 把「程序自身的批量写入（加载/放置/回滚）」当成用户修改 → `scheduleAutoSave` → 回流重载 → 又一条死循环。
**修复B**: 守卫标志**必须在命令触发时同步快照**：`skipByGuardAtFireTime = isPlacingFieldRef.current || isRestoringRef.current || isLoadingRef.current || isStructuralRef.current`（在 `setTimeout` 之前计算，且在 `isStructuralRef.current = true` 置位之后），延迟体内改用该快照判定。
**经验（铁律补充）**:
- **凡被 setTimeout/微任务延迟的处理体，禁止在体内存取"当时状态"型标志**——这些标志往往在延迟前就被复位。必须在事件触发的同步段快照，再传入延迟体使用。
- **一个函数若既内部回调又返回值给调用方再回调，两种数据的形状必须都纳入"自产变化"识别**，否则签名/引用判定必然失配。
- 现象「反复弹加载成功/面板灰变黑/属性不生效」通常是**重载死循环**的外在表现，先查回流重载链路，不要孤立地修面板或属性逻辑。
**验证**: lint 0 错误。待停 dev server 重启+硬刷新实测：①不再反复弹 toast；②增删行/列后字段面板保持置灰；③只读/可编辑/必填切换生效。

## 续38: 只读/可编辑/必填切不动——setFieldAttr 只改了一个元数据对象（标签格与字段格是两份独立拷贝）
**现象**: 右键「只读/可编辑/必填」后日志一切正常（`[setFieldAttr] 设置字段属性: fieldId=3112, attr=1, name=field_14`、Map 有 `7_2`、保存也成功且被识别为自保存跳过 reload），但单元格外观**完全不变**。
**根因（关键数据模型事实）**: `cellFieldMetaMap` 里**标签格与字段格是两个互相独立的对象**——`loadLayoutData` 对每一格各做一份 `{...cell.fieldMeta}` 拷贝（如 `7_1` 标签 + `7_2` 字段，同 fieldId、同 fieldName，但不同引用）。
而 `setFieldAttr` 第 ④ 步只更新了 `baseMeta`（按 fieldName 在 Map 里 `forEach` 取到的**最后一个**匹配项，可能是标签格那份），第 ⑤ 步写回时却用**每一格各自的 `meta`**。
决定外观的正是「字段格」那一份：`getCellDisplayValue` 用 `meta.fieldAttr` 拼图标（214 行：1→🔒、3→⚠️），`applyFieldAttrStyle` 用 `meta.fieldAttr` 定底色（185-191 行，且 only `cellType==='field'` 生效）。
→ 若 baseMeta 命中的是标签格那份，字段格仍按**旧** fieldAttr 渲染 → **「切了没效果」**。旧注释「baseMeta 是引用，Map/布局里同一对象会被同步」是**错的**。
**修复**: 第 ④ 步改为按 `fieldId` 遍历 `cellFieldMetaMap` 更新**全部条目**的 `fieldAttr/required/readonly`（baseMeta 自身也同步一次，覆盖其来自布局兜底、不在 Map 中的情况）。
**安全边界**: `applyFieldAttrStyle`(182) 仅对 `cellType==='field'` 生效、`getCellDisplayValue` 对 label 只返回标签文字 → 更新全部条目不会污染标签格外观。
**经验（铁律补充）**: **一个字段在 `cellFieldMetaMap` 中占两格（标签/字段）且是两份独立对象。任何"按字段更新属性"的操作都必须按 `fieldId` 遍历更新全部条目**，不能只改单个对象——否则改的那一格恰好不负责渲染，就表现为「操作成功但界面无变化」这类最难查的假成功。
**验证**: lint 0 错误。待停 dev server 重启+硬刷新实测：右键切换只读/可编辑/必填，单元格图标（🔒/⚠️）与底色即时变化。

```js
const cur = getCur(r,c);
if (label && cur!=null && String(cur)===label) { put(key,meta); return; }     // ① 本格文字仍在
if (label && labelTextIndex[label]) { ... put(spot); return; }                // ② 文字平移到别处 → 搬回
if (cur===null||cur===undefined||String(cur)==='') { removeFieldCompletely(...); changed=true; return; } // (a) 清空=删除
const curName = extractFieldNameFromDisplay(cur);
if (curName) { removeFieldCompletely(...); changed=true; return; }            // (c) 本格变别的字段占位符=孤儿
(meta as any).fieldLabel = String(cur); if (put(key,meta)) changed=true;      // (b) 改名 → 同步 fieldLabel 保留
```
**关键反例（先修一版踩的坑）**: 若只写"文字消失就删"，会把「重命名标签」误删——`set-range-values` 处理器对标签编辑是 `return` 忽略的（line 3114 `if (meta.cellType!=='field') return;`），于是 `meta.fieldLabel` 仍是旧文字 → reconcile ② 找不到旧文字 → 误判"消失"→ 删字段。故必须区分**清空**(a)/**改名**(b)/**占位符覆盖**(c) 三态，改名只同步 `fieldLabel`。
**经验（铁律）**: 凡"某格内容没了"的处理，必须先区分**清空 vs 改写**——同一 `cur!==label` 既可能是用户删除（应移除）也可能是用户改名（应保留+同步属性），两者动作完全不同，绝不能一概删除。标签/字段名这类"允许用户自由编辑文字"的元数据时尤其如此。结构性平移（文字仍在表中别处）由 ② 单独兜住，不会落入删除分支。
**验证**: lint 0 错误。待重启实测：①清空标签（相邻/不相邻布局）→ 面板立即变黑、两格清空、可重拖；②改名标签 → 面板仍置灰、字段不丢、`fieldLabel` 同步更新；③插入/删除行或列后标签文字平移 → 仍保留并搬回正确位置（不误删）。

## 续45: 预览中明细表不显示（extractSheets 不认 parentData 形状）
**现象**（用户报：ExcelPreviewPage 预览里明细表整块不出现）：主表正常，但明细表无论在标记处内联还是底部兜底都渲染不出来。

## 续50: 手机模式明细表「字段标签名重复列一排」修复
**现象**: 手机模式明细表内，字段名被重复渲染（先出现一排标签，接着字段行又各带一次标签）。
**根因**: 明细表子画布的典型布局是「**第 0 行表头标签 + 第 1 行字段**」。原 `extractMobileItems` 只跳过「右侧紧邻字段」的标签格（横向成对布局），表头行标签是被**下方**字段消费的，未被跳过 → 被当成 `title` 分区标题单独成行，随后字段行又通过 `findLabelCell` 取到同一标签 → 重复。
**修复**（ExcelPreview.tsx 的 `extractMobileItems`，两遍扫描）：
- `findLabelNear`（只返文案）→ 改为 **`findLabelCell`**（返回 `{row, col, label}`）。
- **第一遍**：遍历所有 `cellType==='field'` 格，用 `findLabelCell` 算出其消费的标签格坐标，加入 `consumedLabels` 集合。
- **第二遍**：遇到 `cellType==='label'` 格，若命中 `consumedLabels` 则 `return`（不再单独成行）；字段格改用 `findLabelCell(...)?.label` 取标签。
- 效果：横向成对（左标签右字段）与纵向表头（上标签下字段）两种布局都不会重复；未被任何字段消费的独立标签仍渲染为分区标题。

## 续51: 明细表批量删除（勾选 + 全选 + 删除选中）
**需求**: 明细表支持批量删除（对齐 ecology `delRowFun` 的 `check_mode_{groupid}` 行选择框 + `check_all_record` 全选）。
**实现**（ExcelPreview.tsx）:
- 新增 state `detailSelectedRows: Record<idx, number[]>`（选中行号），`open` 重置时一并清空；单行 `handleDeleteDetailRow` 会同步修正选中项（>rowIdx 前移 1、去掉被删行），避免索引错位。
- 新增三个处理器：
  - `handleToggleDetailRow(idx, rowIdx, checked)`：勾选/取消单行，结果排序去重。
  - `handleToggleAllDetailRows(idx, checked)`：全选=生成 `[0..rowCount-1]`（依赖 `detailRowCounts`）。
  - `handleDeleteSelectedDetailRows(idx)`：一次删多行。先算 `remain=[0..N-1] \ selected`，建 `remap: 旧行号→新行号`（顺序不变），用 `rowRe = /^dt{idx}__r(\d+)__(.*)$/` 重写 `formValues` 与 `errors` 的 key，`rowCount = Math.max(1, remain.length)`，清空该 idx 选中。**注意**：全选删除后 remain 为空 → 保留 1 个空行。
- `DetailBlock` 新增 `selectedRows/onToggleSelect/onToggleSelectAll/onDeleteSelected`：每行头部加 `Checkbox`；底部操作条改为「全选(indeterminate 半选) + 删除选中(n) + 新增行」。
- 属性贯通：`SheetPreviewForm`（PC 内联标记）、`MobileSheetForm`（手机端明细卡片）、`pcContent`/`mobileContent` 的孤儿明细表块，全部补齐 4 个批量删除入参（用 replace_all 一次性改 PC/手机两处）。
