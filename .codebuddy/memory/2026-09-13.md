## PUT /definition/{id}/bpmn 报 400 的根因（已定位）
- 现象：前端保存画布 `PUT .../bpmn` 400，控制台 `BladeRestExceptionTranslator`。
- 根因不是前端/源码：源码与磁盘 `target/classes` 都已用 `BpmnSaveDTO`（已 `findstr` 确认 `WfDefinitionController.class` 含 `BpmnSaveDTO` 引用）。而是**运行中的 blade-workflow 实例陈旧**——进程 PID 17496 启动于 `2026-09-12 11:54:59`，早于修复编译时间（22:55），JVM 加载的是修复前旧 class（旧 body 签名取不到 `bpmnXml` → `saveBpmn` 抛 "BPMN 内容不能为空"）。
- ⚠️ 关键机制：`blade-tool` 的 `BladeRestExceptionTranslator` 把 `ServiceException` 用 `@ResponseStatus(HttpStatus.BAD_REQUEST)` 映射成 **HTTP 400**（不是 200+success=false）。所以 workflow 里任何 `ServiceException`（"流程定义不存在"/"BPMN 内容不能为空"/"BPMN 解析失败"）在前端都表现为 400。
- 注意端口误判：本机 8400 是 **formmode** 服务（`FormmodeApplication`），不是旧 workflow 实例；workflow 仅 8111 一个实例。
- 处理：已 `taskkill /PID 17496`。用户需在 IDEA 重新 Run/Debug `WorkflowApplication`（会重建并加载含 BpmnSaveDTO 的 class），重启后保存画布即正常。

### ⚠️ PUT /bpmn 报 "BPMN 解析失败：Error reading XML"（已修，真因=SpringBlade XSS 去标签）
- 现象：bpmnXml 已正常传到后台（"内容不能为空"已解决），但 flowable 7.1 `BpmnXMLConverter.convertToBpmnModel` 抛泛化 "Error reading XML"（底层 `XMLStreamException` 被包掉，真实 cause 看不到）。
- **真实 cause**（`log.error` 打出 `headHex` 后确认）：`javax.xml.stream.XMLStreamException: ParseError at [row,col]:[5,7] Message: 前言中不允许有内容。`。`headHex` 解码首字节为 `\n\n  \n    \n      Flow_1tj6on4...`——**完全没有 `<`**，证明到达后台的 bpmnXml 不是 XML，而是 `<...>` 标签被删光后剩下的"文本+缩进"。真凶是 `blade-core-tool` 的 `XssHttpServletRequestWrapper` + `XssHtmlFilter`：请求体过 XSS 时白名单仅 `a/img/b/strong/i/em`，BPMN 的 `<bpmn:*>` 整段被删。**与 bpmndi / camunda / BOM / 前导乱码无关**（早先的"prolog/BOM"判断是误判）。
- 修复：`WfDefinitionServiceImpl.saveBpmn` 解析段——**先规范化**：`docStart = indexOf("<?xml")` 再退而 `indexOf("<bpmn:definitions")`，若 >0 则 `substring(docStart)` 去掉前导内容；用 `final String xmlInput` 承接（lambda 要求 effectively final）。主解析失败再剔除 `<bpmndi:BPMNDiagram>` 重试；仍失败则把**完整 bpmnXml 落盘 `d:/temp/bpmn_<defId>.xml`** + 打前 64 字节 hex（`headHex`），并把真实 cause 返回前端。
- 注：`convertToBpmnModel(stream,false,false)` 第三参 `enableSafeBpmnXml=false`；第二参 `validateSchema=false`。
- ⚠️ IDEA 还原坑（实测仍发生）：`replace_in_file` 写已打开的 java 会被 IDEA 回滚（磁盘变回旧版）。可靠做法：写补丁 `.ps1`（`[IO.File]::ReadAllText`→`Replace`→`WriteAllText(tmp, UTF8Encoding($false))`→`Move-Item -Force` 覆盖）→ 以 `Get-Content` 验真实磁盘 → `mvn ... compile` 见 "Recompiling... because of changed source code" 即生效。
- ⚠️ 全局替换 `bpmnXml.getBytes`→`xmlInput.getBytes` 会误伤**同文件其它方法**（部署/条件注入方法 711 行只有 `bpmnXml` 无 `xmlInput`→编译报"找不到符号"）；lambda 捕获的局部变量须 `final`/`effectively final`（重赋值会报 lambda 变量非 final）。

## ⚠️⚠️ 版本功能 404 事故：IDEA 回滚 + mvn 增量编译假象 + ps1 CRLF 坑（三连）
- 现象：`GET /definition/{id}/versions` 404 No mapping，但进程(19:24:09)比 class(19:23:20) 新、`mvn compile` BUILD SUCCESS。
- **根因链（三层叠加）**：
  1. **IDEA 用 VFS 旧源码覆盖编译**：19:23 IDEA Run 前 Build 时未感知我 19:10 的外部修改 → 用旧源码编译出旧 class 写入 target/classes（mtime 变新）。
  2. **mvn 增量编译被骗**：class(19:23) 比源文件(19:10) 新 → `mvn compile` 跳过 → BUILD SUCCESS 但产物仍旧。**mvn BUILD SUCCESS ≠ 生效，必须 `javap -p -classpath target\classes 类名` 验证方法存在**；用 `clean compile` 强制重编。
  3. **IDEA 部分回滚实锤**：重新用 replace_in_file 写的 Controller/IService/Impl 三个**在 IDEA 打开过**的文件被缓冲区回滚（同批的实体/VO/yml 未打开者完好）。最终用 `.ps1` 锚点替换重打 9 处补丁（`Norm(CRLF→LF+孤\r→LF)` 双向归一 + SKIP-ALREADY 幂等 + 写后 findstr/javap 回读校验）。
- **⚠️ ps1 here-string 双坑（新）**：
  1. `'@ 'TAG'`（结束符同行跟参数）非法——`'@` 必须独占行首；应写 `$o = @' ... '@` 变量式再传参。
  2. **write_to_file 写的 .ps1 是 CRLF 行尾 → here-string 字符串字面量内含 `\r\n`**；若 Patch 把目标文本归一成 LF 而 $old 仍是 CRLF → Contains 永远 false → 全部 MISS。**Patch 函数必须对 text/old/new 三方都 Norm**（`Replace("\`r\`n","\`n").Replace("\`r","\`n")`），文件里还可能有 CRCRLF 残留（Replace 后会再生 CRLF，孤 \r 必须单独处理）。
- 教训：改 IDEA 打开着的文件后，除了 Reload from Disk 提醒，**重编译一律 clean compile + javap 终验**；"工具报成功 + mvn 成功 + 进程已重启"三者齐了仍可能 404，必须验证 class 字节码。
- 用户需在 IDEA `File → Reload All from Disk` 后重启 WorkflowApplication（本次已由 clean compile 把新 class 放入 target/classes，若 IDEA Run 前自动 Build 且 VFS 已刷新则无碍；若又 404 说明 IDEA 再次用旧缓冲覆盖 → Reload 后重启）。

## ⚠️ saveAsNewVersion 版本号冲突事故 + max+1 修复 + 锚点回填
- 现象：`Duplicate entry 'flow_mtzfnxjvun1s-2' for key uk_proc_key_version`。原逻辑 `newVersion = old.getVersion()+1`：用户反复点另存已生成 v2/v3/v4，再基于 v1 生成仍算 ver2 撞键。
- **修复**：版本号改为「同 procKey 最大值+1」（`defMapper.selectList(eq procKey)` 取 max+1，不依赖锚点），唯一键兜底并发。
- **脏数据回填**：用旧/新代码生成的 v2/v3/v4 的 `active_version_id=NULL`（旧代码无 setActiveVersionId），导致版本组查询分裂。幂等回填 SQL：`UPDATE wf_process_definition w JOIN (SELECT proc_key, MIN(id) anchor FROM ... GROUP BY proc_key) g ON w.proc_key=g.proc_key SET w.active_version_id=g.anchor WHERE w.active_version_id IS NULL OR <> g.anchor`（把组内锚点统一为该组最小 id）。已执行：回填 5 行，flow_mtzfnxjvun1s 现 4 版锚点=v1.id。
- 教训：`saveAsNewVersion`（以及任何「序号/版本号」生成）必须取**组内最大值+1**而非「当前对象+1」，否则已有更高序号时唯一键冲突；与 ecology WorkflowVersion 的 max+1 一致。
- 清理测试版本（可选，逻辑删除安全）：`UPDATE wf_process_definition SET is_deleted=1 WHERE id IN (<v2,v3,v4的id>)`（保留 v1=2099022450722361345）。
