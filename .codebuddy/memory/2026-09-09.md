## 登录报 NoSuchMethodError: User.getRoleId()（Lombok 未生效）

## blade-auth 启动失败根因（Feign fallback 扫描范围，系统性）
- **真因**：`blade-core-cloud-5.0.1.jar` 的自定义 `BladeFeignSentinel` 严格要求 Feign `fallback` 必须是 Spring Bean（`getFromContext` 去容器 `getBean`）。报错 `IllegalStateException: No fallback instance of type ...IUserClientFallback found for feign client blade-system` 即 fallback 不是 Bean。
- **为什么不是 Bean**：`@BladeCloudApplication`（≈`@SpringBootApplication`）默认只组件扫描**本模块包**（如 `org.springblade.auth`），而 `IUserClientFallback` 是 `@Component`，位于 api 模块包 `org.springblade.system.user.feign`，不在扫描范围内 → 不是 Bean → 启动失败。对照 `blade-system` 用 `@SpringBootApplication`（默认扫 `org.springblade.system`）+ 显式 `@EnableFeignClients(basePackages={...,"org.springblade"})`，其扫描基包恰好覆盖 `org.springblade.system.user.feign`，所以 system 能解析到 fallback（这也是 system 不用 @BladeCloudApplication 的原因）。
- **修复（已全量应用）**：给所有 13 个用 `@BladeCloudApplication` 的启动类加 `@ComponentScan(basePackages = "org.springblade")`（与 `@EnableFeignClients` 扫描范围对称），使 api 模块的 fallback `@Component` 被注册。`blade-auth` 还加了注释说明。涉及：auth / workflow / pay / order / mall / log / demo / formmode / resource / desk / report / develop / admin。
- **注意（潜在同类隐患）**：`blade-system`、`blade-gateway` 走 `@SpringBootApplication`+显式 `@EnableFeignClients("org.springblade")` 模式，默认只扫各自包。若它们消费**跨包**的 fallback（如 `blade-system` 消费 `IPayClient`→`org.springblade.pay.feign.IPayClientFallback`），仍会复现 `No fallback instance found`；届时可同样补 `@ComponentScan("org.springblade")`。`blade-system-api` 的 fallback 多在 `org.springblade.system.feign` 下（被 system 自带扫描覆盖），故当前未暴露。
- **排查 Feign 启动失败的统一套路（更新）**：① fallback 类有 `@Component`；② **消费方启动类组件扫描覆盖 api 模块包**（`@ComponentScan("org.springblade")`）；③ 本地临时 `feign.sentinel.enabled:false` 验证是否 sentinel 集成问题；④ Nacos 已起。

## Redis 缓存反序列化失败（升级后残留旧序列化数据）
- 现象：`GET /user/info` 报 `SerializationException: Cannot deserialize ... invalid stream header: 0A1FCA01`（JdkSerializationRedisSerializer 反序列化失败）。根因：**升级到 Spring Cloud 2025.1 / Boot 4 前，旧版 blade-system 把 `SYS_CACHE` 域写进了这台 dev Redis，用的是另一种序列化格式**；新应用用 `RedisCacheManager` 默认的 JDK 序列化器去读 → 魔数不匹配 → 崩。
- 关键：这是**读旧数据**失败，不是代码 bug（`SysCache` 用 `CacheUtil` 读写同一 `RedisCacheManager`，新写必为 `AC ED 00 05`，不可能写出 `0A1FCA01`）。清掉脏数据即可，下次请求从 DB 重载并写回当前格式。
- **dev Redis 连接信息（Nacos `blade-dev.yaml`）**：`host=127.0.0.1`、`port=6379`、`password=123456`、`database=0`。
- **缓存真实名字不是 `SYS_CACHE`**：Nacos 配了 `spring.cache.redis.key-prefix=blade:`，所以 `SYS_CACHE` 在 Redis 里的真实 cache 名为 **`blade:sys`**（键形如 `blade:sys::role:names:...`）。因此 `redis-cli --scan --pattern 'SYS_CACHE*'` 匹配不到，须用 `blade:sys*`。
- **本机无 `redis-cli`**：`redis-cli` 不在 PATH、常见目录也没有，原命令无法直接跑。改用 actuator 清缓存（Nacos `management.endpoints.web.exposure.include: "*"`，未单独设 management 端口 → 在 `blade-system` 的 8106 上）。`GET /actuator/caches` 返回结构 `cacheManagers.redisCacheManager.caches`，名字即 `blade:sys`。
- **已执行**：`DELETE /actuator/caches/blade%3Asys` → `204`，`blade:sys` 缓存域清空。用户无需重启，再访问 `/user/info` 即重建并正常。
- 同类问题（其它 `blade:*` 域有旧格式）：同样用 actuator `DELETE /actuator/caches/blade:xxx`，或 `DELETE /actuator/caches` 清全部应用缓存域。
- 增强建议（未做）：把 `blade-system` 的 `RedisCacheManager` 显式配成 JSON 序列化（`GenericJackson2JsonRedisSerializer`），避免以后再因二进制格式不兼容直接 500；当前清缓存已能跑通。

## blade-formmode 接口全部 401「请求未授权」根因与修复
- 现象：`GET /form-definition` 等 formmode 接口全部抛 `org.springblade.core.secure.exception.SecureException: 请求未授权`（被 `org.springblade.formmode.config.GlobalExceptionHandler` 捕获记 "运行时异常"）。Token 有效且 `role_name=administrator`、`role_id/user_id/dept_id` 均在、未过期。
- **根因**：formmode 的 6 个控制器用了 `@PreAuth("hasPermission('formmode:bill:view')")` 这类**自定义权限码**注解，但：
  1. `hasPermission` 的实现者 `ApiScopePermissionHandler implements IPermissionHandler` 位于 **`blade-scope-api`**，而**整个仓库没有任何 pom 依赖 `blade-scope-api`**（0 处），`blade-formmode` 的 pom 也没有 → 无 `IPermissionHandler` Bean；
  2. `hasPermission` 走 `blade_scope_api` 接口权限表（`permissionCode(code, roleId)`），这些 `formmode:*` 码**无任何初始化数据**；
  3. `hasPermission` 在全项目 **103 处 `@PreAuth` 中仅 formmode 这 6 个文件使用**，属自创写法，框架无支撑 → 必然校验失败。

### 第三次报错：nodePermission is not a function（根因 = HMR 跨文件模块陈旧）
- 报错：`FieldCell (ExcelPreview.tsx:376)` `TypeError: nodePermission is not a function`。此时 nodePermission 已能传入（不再是 undefined），但值不是函数 → 说明上游 `ExcelPreviewPage.tsx:70` `setNodePermission(() => (fieldName: string) => {...})` 的产物在运行态是**对象**而非函数。
- 关键机制（务必记牢）：React `useState` 的 setter 会把**函数参数当作更新器执行**（`newState = action(prev)`）。所以 `setNodePermission(resolver)`（无 `() =>`）会被当成更新器 → state 变成 resolver 的返回值（对象 `{readonly,required,hidden}`）→ 后续 `nodePermission(...)` 抛 "not a function"。正确写法是 `setNodePermission(() => resolver)`（`() =>` 被更新器消费掉，state 才等于 resolver 本体）——`ExcelPreviewPage.tsx` 磁盘代码已是对的。
- 真正的运行期病根：**HMR 只重编译了我改动的 `ExcelPreview.tsx`，未重编译 `ExcelPreviewPage.tsx`**，后者仍在跑旧的 `setNodePermission((fieldName)=>...)`（无 `() =>`）→ state 是对象。这印证了"改动跨文件时 HMR 不可靠、必须整服务重启"的老坑。
- 防御改动：`FieldCell`（375 区）与 `SheetPreviewForm`（原 908 行）两处调用点改为 `typeof nodePermission === 'function' ? nodePermission(...) : undefined`，即使哪次又遇到非函数值也只优雅降级、绝不崩溃。
- 结论：磁盘代码已正确，**必须停止 dev server 整服务重启 + 硬刷新**才能让 `ExcelPreviewPage.tsx` 也用上 `() =>` 版本，nodePermission 才会是真正的函数。再次强调：本项目 ExcelDesign/HMR 极不稳定，跨文件改动一律重启验证，不要信 HMR 热更。

### 修正：grant-tree 出现跨租户重复菜单（超管也必须按租户过滤）
- 上一版让「超管租户传 null（不加租户过滤）」是**错的**，用户立刻反馈菜单重复。原因：`blade_menu` 是**按租户各存一份副本**（有 `source_menu_id` 列，各租户菜单 id 不同、名称相同），不加过滤就会把所有租户的同名菜单全查出来。
- 最终做法：`MenuServiceImpl.grantTree/grantDataScopeTree/grantApiScopeTree/grantTopTree(BladeUser)` **一律传 `user.getTenantId()`**（超管与非超管都一样，只有「走全量还是走角色」的分支不同）。
- 另外给 `grantDataScopeTree`/`grantApiScopeTree` 的 `UNION ALL` 第二段（查 `blade_scope_data`/`blade_scope_api` 的叶子节点）补了租户收敛：`AND menu_id IN (SELECT id FROM blade_menu WHERE is_deleted = 0 <if> AND tenant_id = #{tenantId}</if>)`。
  - **不能用 `blade_scope_data.tenant_id` 直接过滤**：`blade_scope_api` 建表语句**根本没有 tenant_id 列**，`blade_scope_data` 也只在较新的 dump（`blade_2026-04-26_093638.sql`）里才有，老 `blade.sql` 没有 → 直接写该列在部分库上会 `Unknown column`。统一走 `menu_id ∈ 本租户菜单` 最安全。
  - ByRole 变体的叶子段本来就带 `menu_id IN (role_menu)` 约束，已天然收敛到本租户，未再改。
- 排同类问题：`SELECT tenant_id, COUNT(*) FROM blade_menu GROUP BY tenant_id` 可一眼看出是否存在多租户副本。
