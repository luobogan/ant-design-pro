# 2026-09-05

## ExcelDesign 字段面板置灰不刷新的根因与修复

**根因**: 删除单元格的字段/字段名后,面板不置灰回黑、已删字段"复活"。原因是 `lookupCellMeta`/`findMetaNear` 的 tier-2 兜底会从旧的 `layoutData` 把字段 meta 重新写回内存 `cellFieldMetaMap` 并挂进保存结果,导致 `usedFieldKeys` 仍含该字段 → 面板继续灰。

**修复(UniverExcelGrid.tsx)**:
1. 墓碑机制: 新增 `removedFieldTombstones` ref + `markFieldRemoved`/`isFieldRemoved`/`removeAllFieldsFromMap`,在 `removeFieldCompletely` 删除时打墓碑,使 tier-2/tier-3 复活逻辑遇到已删字段直接跳过。
2. `notifyFieldsChanged()`: 以内存 Map(字段放置唯一事实源)直接 `window.dispatchEvent('univer-fields-changed', {keys})`,在 `saveLayoutData`(保存后)、`loadLayoutData`(finally)、`removeFieldCompletely`(删除后)三处调用。

**修复(ExcelDesign.tsx)**:
- 新增 `gridUsedKeys` state + 监听 `univer-fields-changed` 事件;`usedFieldKeys` 优先用 `gridUsedKeys`(表格实时上报),回退到 `layoutData` 推导。覆盖清空单元格、整行/整列删除、ctrl+A+delete 清空全文、拖字段/字段名等场景。

**注意**: 该组件有大量预存 `@univerjs` 模块解析告警(16条),非本次引入,无需处理。

## 续:右键"清空"菜单面板不刷新的真正根因(第二次修复)

**根因**: 右键"清空"菜单派发 `univer-cell-clear`(派发点在 `src/univer-lib/sheets-ui/lib/es/index.js:71`,空 detail),由 `handleCellClear` 处理。原代码:
```js
if (!findMetaNear(row, col)) { /* 像素吸附兜底 */ }
gridApi.clearCell(row, col);   // 仍用偏移后的命中格坐标
```
`findMetaNear` 在右键命中偏移(文档实测达 2 列:字段在 (1,1) 命中 (1,3))时能找到附近字段 meta,但**只返回不回写坐标**;且 `if (!findMetaNear)` 找到时整体被跳过。`clearCell` 用偏移坐标查 `cellFieldMetaMap` 为 undefined → 走"普通单元格"分支,只清空格值、**不动真实字段格 meta** → 字段元数据残留 → 面板始终灰。

**修复(UniverExcelGrid.tsx `handleCellClear`)**:
- 采用 `findMetaNear` 修正后的坐标(`near.key`)作为清空目标;仅当附近查不到字段时才像素吸附兜底。
- 若目标为「标签格」,反查同字段的「字段格」再清空(使 `removeFieldCompletely` 整字段移除两格),确保字段整体恢复可拖、面板变回黑色。

面板刷新机制(notifyFieldsChanged → univer-fields-changed → ExcelDesign.gridUsedKeys → usedFieldKeys → FieldPalette 置灰)本身正确,此前不刷新纯因字段 meta 从未被真正删除。

## 续2: 删除字段后再次拖入被"已放置"拦截 + 面板刷新不及时

**现象**: 右键清空(或键盘删除)字段后,字段面板刷新不及时;且删除 `${xx}` 字段后再次拖入"不生效"(被 `handleFieldDrop` 唯一性校验判为已放置而拒绝)。

**根因**: 重拖唯一性校验(`handleFieldDrop`,约 1679-1739 行)的 `properlyPlaced` 只看 `placedInMap / placedInLayout / placedInSheet` 四个来源,**没有把"已显式删除(墓碑)"作为放行条件**。一旦删除后 Map / 持久化 layoutData / 表格残留占位符任一处因时序仍判为"已放置",重拖就被拒。

**修复(UniverExcelGrid.tsx)**:
1. 重拖校验加入墓碑放行: `wasExplicitlyRemoved = removedFieldKeysRef.current.has(dropIdKey)`;若字段被显式删除过(墓碑存在),强制 `properlyPlaced = false` 放行重拖。`removeFieldCompletely` 删除时 `markFieldRemoved` 已对 `${fid}_label`/`${fid}_field` 打墓碑,`setCellField` 重拖时再清除该墓碑。
2. `handleFieldDrop` 中 `setCellField` 之后立即调 `notifyFieldsChanged()`,使面板置灰不依赖 `saveLayoutData` 的全表扫描,刷新更即时。

**注意**: `saveLayoutData` 只在内部调 `onLayoutChange`(通知父组件),不再直接写 `layoutDataRef`;但 `layoutDataRef.current` 在组件 853 行每次渲染同步为 `layoutData` prop,父组件 `onLayoutChange→setLayoutData` 重渲染后即更新,故跨用户操作的重拖读到的是新值(墓碑放行是更稳健的兜底)。

## 续3: 清空单元格后面板仍不刷新(真正根因:标签格"仅释放标签"违反整字段语义)

**现象**: 清空单元格(右键菜单/键盘 Delete)后,字段面板置灰状态不变。

**排查结论(逐条排除)**:
- `notifyFieldsChanged → univer-fields-changed → ExcelDesign.setGridUsedKeys → usedFieldKeys → FieldPalette` 链路正确;`removeFieldCompletely` 内部确实 `delete` Map 键(1489)并 `notifyFieldsChanged`(1495)。
- `getCellFieldMeta`(974)只从 Map 读,**无 tier-2**,故 `saveLayoutData` 不会复活已删字段。
- `isLoadingRef` 在 `finally`(1169)复位,不会卡住早退守卫(2289/2381)。
- `ClearCellCommand` 只在改过的 univer-lib(`src/univer-lib/sheets-ui/lib/es/index.js:67-74`)里 `dispatchEvent('univer-cell-clear')`,**自身不做任何清空**,全部逻辑依赖本组件的 `handleCellClear`。
- `window.univerExcelGrid.clearCell` 已在 2819 行暴露,桥接正常。

**根因**: `removeFieldCompletely` 上方注释(1458-1461)约定"清空/删除**任意一格**时必须同时清掉另一格并移除两处元数据",但三条清空链路的**标签格分支都只释放标签、不清 `${xx}` 占位符格**,导致字段的 `_field` key 与占位符残留 → 面板恒灰:
1. `clearCell`(2775-2782 旧):命中标签格走"仅释放标签"分支。
2. `onCommandExecuted` 的 `clearedLabelKeys`:仅 `markLabelRemoved` + 删本键。
3. 防篡改守护定时器(2419 旧):同上。
且 `handleCellClear` 的"标签→字段格重定向"(3193-3212)只在 Map 中存在 `cellType==='field'` 的元数据时才生效,而 2972 行注释实测"元数据挂在标签格上" → 重定向失效。

**修复(UniverExcelGrid.tsx)**: 三条链路统一为**整字段移除**
1. `clearCell`: 先用 `lookupCellMeta(row,col)`(本格 + ±1行/±3列 + tier-2 布局 + tier-3 表格内容)吸附到真实字段格;命中标签或字段**统一**调 `removeFieldCompletely`(同时移除两格元数据与单元格值、对两格打墓碑)。
2. `onCommandExecuted` 的 `clearedLabelKeys`、守护定时器标签分支:同样改调 `removeFieldCompletely`。
3. 删除已无引用的 `markLabelRemoved`(被 `markFieldRemoved` 取代),同步三处过时注释。

**设计约定(重要)**: 一个字段 = 标签格 + 字段占位符格,两格在 `usedFieldKeys` 中**各自独立计数**(`${fieldId}_label` / `${fieldId}_field`)。清空任一格都必须整字段移除,否则残留另一格的 key 与占位符。

## 续4(用户贴日志后定位): 「孤儿字段元数据」——清空后面板不刷新的真正根因

**日志证据**:
```
[Save] 保存前 Map keys = (9) ['0_0','0_1','1_0','1_1','2_0','2_1','3_0','3_1','5_0']
[Save] 写入的 fieldMeta 数量 = 6   Map 剩余 keys = 9
```
Map 有 9 条但只有 6 个单元格真有值 → **3 条孤儿元数据**(单元格已空、Map 仍留着)。

**根因**: `saveLayoutData` 扫描时对空值单元格 `continue`(跳过),这些条目**永远进不了 cellData、也永不被清理**;而 `notifyFieldsChanged` 是**以 Map 为准**广播的 → 已清空的字段在面板上**永久置灰**。此前几轮修复都只改清空链路,没动这个"Map 与表格不一致"的根源,所以现象一直复现。

**修复(UniverExcelGrid.tsx `saveLayoutData`)**: 在 `notifyFieldsChanged()` **之前**插入孤儿校正:
- 条件 `!isPlacingFieldRef && !isLoadingRef && !isRestoringRef`;
- 对 Map 每条读 `sheet.getRange(r,c).getValue()`,为空则 `removedFieldKeysRef.current.add(tombstoneKey(m))`(仅本 cellType 打墓碑,防 tier-2 复活)+ `delete` 该键;
- `GRACE_MS = 2000`:依据 `__timestamp`(`setCellField` 写入)给刚放置的字段宽限期,避免 `setValue` 尚未生效被误删。

**诊断口诀**: 日志里 `写入的 fieldMeta 数量 < Map 剩余 keys` 即存在孤儿;修复后两者应相等。

**推论**: 置灰状态以内存 Map 为唯一事实源,因此 Map 必须能被"表格实际内容"校正,否则任何一处清空漏删都会永久污染面板。

## 续5: 先拖 ${xx} 字段、再拖标签导致 ${xx} 丢失 + 标签不带属性状态 + 拖动配色

**Bug 根因(handleFieldDrop 的"僵尸格"兜底误伤)**:
拖「标签」时扫描表格用的匹配式是 `sv.includes(dropName)`,而字段占位符文本是 `${field_12}`——它**文本上就包含 `field_12`**,于是命中被判定为"标签残留僵尸格",随后被 `zr.setValue('')` 清空 → 已放置的 `${xx}` 字段被删。顺序依赖:先拖字段(表里已有 `${xx}`)、再拖标签必现。

**修复(UniverExcelGrid.tsx,两道防线)**:
1. 匹配式加 `!sv.includes('${')`:拖标签时排除一切占位符格(占位符属于字段那一半,不是标签)。
   ```js
   (dropType === 'label' && !sv.includes('${') &&
     ((dropName && sv.includes(dropName)) || (dropLabel && sv.includes(dropLabel))))
   ```
2. 清空僵尸格前查 `cellFieldMetaMap`:目标格若仍持有**有效元数据**就跳过清空(它很可能是同一字段的另一半)。这条是通用护栏,覆盖匹配式漏掉的所有场景。

**标签不显示只读/必填/可编辑**: 原本就成立——`getCellDisplayValue`(200)对 `cellType==='label'` 只返回标签文本;`applyFieldAttrStyle`(176)对非 field 直接 return。为显式化并防止回归,在 `handleFieldDrop` 构造 meta 时让标签不携带属性:`required: isLabel ? false : ...`、`readonly: isLabel ? false : ...`。标签**仍完整保留可拖动能力**(`canDrag: !disabled` 未动)。

**面板拖动配色(FieldPalette.tsx,DraggableLabelItem / DraggableFieldOnlyItem)**:
⚠️ 踩坑:最初把「可拖入(静止)」设成 `#999` 灰、「已拖入」设成 `#ccc`,**两者都是灰**,导致用户"删除后看不到灰色变黑色"。三态必须拉开明度差:
| 状态 | 颜色 | 其他 |
|---|---|---|
| 已拖入(禁用) | `#bfbfbf` 浅灰 | opacity 0.45、图标 `#d9d9d9` |
| 可拖入(静止) | `#262626` 近黑 | — |
| 拖动中 | `#000` 纯黑 | fontWeight 600 |
删除后走 `#bfbfbf → #262626`,一眼可辨;拖动时 `#262626 → #000` 并加粗。

## 续6: 删除后面板仍不变黑 —— 广播缺口 + 最终一致性收敛

**两个真实缺口**:
1. `removeAllFieldsFromMap`(621)**从不广播**;而 auto-clear-content 分支在它之后只调 `scheduleAutoSave()`(防抖)→ 整表清空后面板要等防抖才可能刷新。
2. 守护定时器 `if (keys.length === 0) return;` —— Map 清空时**直接返回、不广播**,面板停留在上一轮置灰状态。

**修复(UniverExcelGrid.tsx)**:
1. `notifyFieldsChanged(force = false)` 增加**签名变化检测**(`lastNotifiedSigRef`,按 `keys` 排序拼接比对):集合不变则不派发。这样守护定时器可每轮安全轮询做「最终一致性校正」,不会因每 800ms 产生新 Set 引用而反复唤醒面板重渲染。
2. `removeAllFieldsFromMap` 末尾加 `notifyFieldsChanged()`。
3. 守护定时器:Map 为空时先广播再 return;每轮扫描结束(forEach 之后、`if (tamperedCells.length === 0) return;` 之前)统一 `notifyFieldsChanged()`。
4. `loadLayoutData` 的 finally 改 `notifyFieldsChanged(true)` 强制广播,覆盖父组件重挂载后 `gridUsedKeys` 被重置为 null 的情况。

**效果**: 无论走哪条删除路径(命令拦截 / 右键菜单 / 键盘 Delete),面板都在 **800ms 内**必然收敛,不再依赖某条链路被正确捕获。

## 续7 ★★★: 删除后面板不变黑的【根本原因】—— 自身保存回流导致字段「复活」死循环

**日志证据(决定性)**:
```
[CellChange] 字段占位符 (0, 1) 已删除，整字段移除   ← 删除已被检测到，removeFieldCompletely 确实执行了
[Guard]      字段占位符 (0, 1) 已清空，整字段移除   ← 800ms 后守护定时器【又】看到同一个字段
```
删除逻辑本身没问题;`[Guard]` 重复出现同一坐标 = **Map 条目删除后又被重建**(否则下一轮不会再见)。

**死循环链路**:
```
removeFieldCompletely（删 Map + 打墓碑 + notify）
  → saveLayoutData()
  → onLayoutChange(parentData) → ExcelDesign.setLayoutData(data)（356 行原样保存、不克隆）
  → 触发「监听 layoutData」effect（2890 行）
  → 该 effect 只挡了 isPlacingFieldRef，没挡自身保存 → setTimeout 100ms 后 loadLayoutData
  → loadLayoutData 清空 Map 且 removedFieldKeysRef.current.clear()（1000 行，墓碑被清空！）
  → 从快照重建 Map → 刚删的字段复活
  → 守护定时器又发现它 → removeFieldCompletely → 保存 → 回流 → 无限循环
```
墓碑被 `loadLayoutData` 清掉是关键一环:复活因此失去唯一拦截手段。

**修复(UniverExcelGrid.tsx)**: 新增 `selfSavedLayoutsRef = useRef<Set<any>>(new Set())`,按**引用**记录本组件自己产出的 layoutData 对象(父组件 `setLayoutData(data)` 不克隆,引用比对可靠):
1. `saveLayoutData` 三个出口分别把 `parentData` / `result` / `emptyResult` 加入集合(超过 6 条自动清空防膨胀)。
2. 「监听 layoutData」effect 开头:命中集合则 `delete` 并 `return`,打印 `[Layout] 本次变化由本组件保存产生，跳过 reload`。
   表格此刻本就是最新状态,重载只会用快照覆盖并清空墓碑,纯属有害。

**排查口诀**: `[CellChange]` 与 `[Guard]` 对同一坐标重复出现 ⇒ 一定是「删了又复活」,优先查回流重载 / 墓碑被清,而不是查删除链路。

## 续8 ★: 改用「轮询兜底」,使面板刷新不再依赖事件链路

事件链路排查多轮仍未根治,故不再把面板刷新押在 `univer-fields-changed` 上,改为**父组件主动向表格轮询查询**。

**改动**:
1. `UniverExcelGrid`: 抽出 `collectUsedFieldKeys(): Set<string>`(从 `cellFieldMetaMap` 汇总 `${fieldId}_${cellType}`);`notifyFieldsChanged` 复用它;并在 `window.univerExcelGrid` 上暴露 `getUsedFieldKeys: collectUsedFieldKeys`。
2. `ExcelDesign`: 新增轮询 effect,每 **700ms** 调 `api.getUsedFieldKeys()`,与 `gridUsedKeys` 比对(内容相同则保持原引用,避免无谓重渲染),有变化才 `setGridUsedKeys(new Set(keys))`。事件监听保留作为快速通道。

**三条诊断日志(用于精确定位断点)**:
- `[FieldsChanged] 广播已放置字段 = [...]` —— 表格侧广播(无此行 ⇒ Map 没清干净)
- `[ExcelDesign] 收到 univer-fields-changed = [...]` —— 事件送达(有上无此 ⇒ 事件链路断)
- `[ExcelDesign] 轮询校正已放置字段 = [...]` —— 轮询发现变化(有此行 ⇒ 面板必然刷新)

**设计原则**: 面板置灰的唯一事实源是表格的内存 Map;凡依赖「事件通知」的 UI 同步,都应有一条主动轮询兜底,否则任一环失效就表现为「UI 不刷新」且极难定位。

## 续11: 撤销/重做按钮（含快捷键）与栈状态实时同步

**需求**: 撤销/重做按钮(或 Ctrl+Z/Ctrl+Y)操作后,按「撤销栈/重做栈是否为空」在灰色(禁用)/黑色(启用)间切换;字段面板操作影响撤销/重做状态时,按钮也实时更新。

**改动**:
- `UniverExcelGrid.tsx`(`window.univerExcelGrid` 构建的 effect 内,`univerRef.current` 已就绪):
  1. 订阅 `undoRedoStatus$` → 立即 `window.dispatchEvent(new CustomEvent('univer-undoredo-status', { detail: { canUndo, canRedo, undos, redos } }))` 并缓存到 `window.__univerUndoRedoStatus`。
  2. API 新增 `undo()` / `redo()` / `getUndoRedoStatus()`(前两者经 injector 取 commandService 执行对应命令)。
  3. effect 返回 cleanup `undoRedoSub?.unsubscribe()`。
- `ExcelDesign.tsx`:
  1. 新增 `canUndo`/`canRedo` state。
  2. 监听 `univer-undoredo-status` 事件更新 state。
  3. 700ms 轮询兜底(复用既有 getUsedFieldKeys 轮询)额外调 `getUndoRedoStatus()` 刷新 state。
  4. `handleUndo`/`handleRedo` 改为调 `window.univerExcelGrid.undo()/redo()`(无 API 时回退 `message.info('撤销功能开发中')`)。
  5. 撤销/重做 Button 加 `disabled={!canUndo}` / `disabled={!canRedo}`。

**注意**: 字段拖入/清空等走 Univer 命令会自动入撤销栈,栈变化即触发 `undoRedoStatus$` → 按钮同步;Univer 内置 Ctrl+Z/Y 同样经同一命令,按钮亦同步。若某操作后字段面板置灰未回滚(如撤销「清空」把占位符写回但未被重新登记到 `cellFieldMetaMap`),属字段跟踪一致性问题,本次未扩展(仅满足按钮状态同步诉求)。

## 续9: 用户核心诉求澄清 —— 要"全量"刷新,不是只处理被删的那一个

用户明确:"是要 刷新字段面板 所有的灰色字段或者字段名 变黑色 不是某一个"。
即：面板置灰应**整体重算**——凡是表格里已不存在的字段（含历史残留孤儿 meta），都应一次性由灰变黑，而不是只处理当前删除的那一个。

**对应实现**：
- 把孤儿元数据清理抽成公共函数 `pruneOrphanFieldMeta(sheet)`：逐条比对 Map 与单元格实际内容，单元格为空且无 2s 宽限期的条目一律 `delete` 并打墓碑。
- 在**守护定时器**每轮（800ms）开头调用 `pruneOrphanFieldMeta(guardSheet)`，清掉所有孤儿后立即 `notifyFieldsChanged()`。这样面板所有误置灰项会**一次性全部变黑**。
- 700ms 轮询（`ExcelDesign` 侧 `getUsedFieldKeys`）随后把这一致状态同步给 `gridUsedKeys`。

**三层保险**：① 删除时 `removeFieldCompletely` 立即广播；② 守护定时器 800ms 全量校正；③ `ExcelDesign` 700ms 轮询兜底。任何一层触发都能让面板在 ~1s 内收敛到"表格里没有的字段全部变黑"。

## 续10: 整行/整列 & 快捷键删除后面板不变黑（残留缺口补充修复）

**残留缺口**: 三层保险对「整行/整列删除」依赖 `handleRowColStructural` 命中 `sheet.command.remove-row/remove-col` 直接重排 Map；对「快捷键删除(auto-clear-content)」旧逻辑只在**清除范围覆盖全部字段**时才 `removeAllFieldsFromMap`，否则仅 `return`，完全依赖 `auto-clear-content` 内部是否再派发 `set-range-values`。若后者未派发、或只删了某个字段格（多字段场景常见），该字段仍留 Map → 面板不变黑（灰色→黑色失败）。

**修复(UniverExcelGrid.tsx)**:
1. `auto-clear-content` 分支改为「部分覆盖也处理」：遍历命中清除范围的字段格/标签格，对覆盖到的字段直接 `removeFieldCompletely(fieldId, fieldName)` 整字段移除（标签/字段任一格命中都移除整字段，与 clearCell 语义一致）；`clearRange` 缺失时回退 `params.range`。`removeFieldCompletely` 内部已 `notifyFieldsChanged`+`saveLayoutData`，面板即时刷新。
2. `handleRowColStructural` 末尾在 `saveLayoutData()` 之后再强制 `notifyFieldsChanged()`，确保即便 `saveLayoutData` 因实例销毁提前 return，面板仍立即由灰变黑。

**注意**: `pruneOrphanFieldMeta`（守卫定时器/保存前）仍只按「单元格为空」移除孤儿——不能改成按「值不匹配」移除，否则会误删被自由改过文字的标签格（违反「标签允许自由改文字」约定）。

## 续12 ★: 撤销后字段面板不变灰（删除→撤销 字段元数据未重建）

**现象**: 删除字段/字段名后点撤销，单元格值被写回，但字段面板不变灰（置灰状态不恢复）。

**根因**: `onCommandExecuted` 的 `sheet.mutation.set-range-values` 处理器对「无 meta 但有值」的单元格直接 `if (!meta) return`，不重新登记。删除时 `removeFieldCompletely` 已把字段从 `cellFieldMetaMap` 移除并打墓碑；撤销把值回灌到单元格，但内存 Map 里没有该字段元数据 → `collectUsedFieldKeys` 不含该字段 → 面板不置灰。（续11 已预判此「字段跟踪一致性」缺口，本次补齐。）

**修复(UniverExcelGrid.tsx)**:
1. 新增 `removedFieldMetaRef`（`${fieldId}_${cellType}`→FieldMeta）暂存被移除字段的完整元数据；在 `removeFieldCompletely`、`pruneOrphanFieldMeta` 删除时写入；`loadLayoutData` 开头 `removedFieldMetaRef.current={}` 清空（权威布局加载后旧暂存失效）。
2. 新增 `findStashedMetaByValue(value)`：遍历暂存按 `getCellDisplayValue(meta)` 精确匹配显示值。
3. `set-range-values` 处理器「无 meta」分支：若 newValue 非空且 `findStashedMetaByValue` 命中 → 置 `isRestoringRef` 调 `setCellField(fWorkbook, getActiveSheet||sheetRef, row, col, restored)` 重新登记（写入 Map + 清该格墓碑 + 上 fieldAttr 样式）；再用后清该墓碑、清暂存项，`notifyFieldsChanged()`+`scheduleAutoSave()` 使面板立即置灰。覆盖字段占位符(`${字段名}`文本)与标签文字两种回灌。

**验证**: 改完停 dev server 重启 + 硬刷新（本组件 HMR 不稳定）。日志应见 `[UndoRestore] 撤销恢复字段 (r,c)…`，随后 `[FieldsChanged] 广播已放置字段` 含该字段。
**误判风险(低)**: 删除后在撤销前手动在空白格敲入与暂存标签文字完全一致的文本会误登记；因暂存为一次性(登记后即清)+loadLayoutData 清空，实际概率极低，未加额外围栏。

## 续19: 明细表标记删除后「孤儿明细表/失效」修复（用户报 整行整列/快捷键删除 明细表失效）

## 续20: 整行/整列删除后「明细表单元格仍出现」根因与加固
**现象**: 用户报「整行整列删除 明细表的单元格还会出现」——删行/列后，主画布里"明细表N"格又出现（但已不是真正标记，点击打不开）。
**根因**: `handleRowColStructural` 只命中写死的命令 id（`sheet.command.remove-row/col` 等）且只认 `params.range` 单对象。若 Univer 实际用复数/别名 id（`remove-rows`/`delete-row`…）或 `params.ranges`（数组），该分支直接 `return`，**`cellFieldMetaMap` 不平移**。于是 Univer 把标记值随行/列平移到新坐标，但元数据仍钉在旧坐标；刷新/重存后该值被当成普通文本写回 → "明细表N"反复出现。
**加固**(UniverExcelGrid.tsx):
1. 调度分支改为正则 `/sheet\.command\.(remove|delete|insert)-(row|col)/i`，覆盖各版本 id 形态。
2. `handleRowColStructural` 兼容 `params.range || params.ranges[0]`，坐标取 `startRow/endRow` 或 `start/end` 兜底；`isRow`/`isRemove` 用 `/row/`、`/(remove|delete)/` 判定。
3. `saveLayoutData` 新增**与命令 id 无关的安全网**: 遍历单元格时若某格显示值=某 `detailTableMarker` 元数据的 `fieldLabel`、且旧坐标已空，则把该元数据认领回新坐标（`cellFieldMetaMap` 旧键删、新键置），杜绝标记被平移成孤儿普通文本。
**验证**: lint 0 错误。待用户停 dev server 重启+硬刷新验证：删除含标记的整行/列后，标记应彻底消失（不再复发）；删除无关行/列则标记随平移、点击仍可用。
