# 表单建模 - 表单管理与字段管理关联交互功能

## 功能概述

实现了表单管理模块与字段管理模块的关联交互功能，支持从表单创建无缝跳转到字段配置，形成完整的表单与字段级联创建闭环。

## 实现的功能

### 1. 表单新增后的"下一步"功能

**文件**: `src/pages/FormMode/FormManage/FormManageAae.tsx`

**实现方式**:
- 在表单新增成功后，显示 `Modal.confirm` 对话框
- 提供两个选项：
  - **"下一步：配置字段"**: 跳转到字段新增页面，并传递新创建表单的 ID
  - **"返回列表"**: 返回表单管理列表页面
- 通过 `formApi.create(data)` 的返回值获取新创建表单的 ID

**代码位置**:
```typescript
// 显示下一步选项
Modal.confirm({
  title: '表单创建成功',
  content: '表单已创建成功，是否立即配置字段？',
  okText: '下一步：配置字段',
  cancelText: '返回列表',
  onOk: () => {
    // 跳转到字段管理的新增页面，并传递表单ID
    navigate(`/formmode/fieldmanage/aae?mode=add&formId=${result.id}`);
  },
  onCancel: () => {
    navigate('/formmode/formmanage');
  },
});
```

### 3. 字段管理页面接收表单 ID 并自动选择

**文件**: `src/pages/FormMode/FieldManage/FieldManage.tsx`

**实现方式**:
- 从 URL 参数中获取 `formId`（通过 `useSearchParams` hook）
- 在组件初始化时，将 `selectedFormId` 状态初始化为 URL 中的 `formId`
- 在 `fetchFormList` 函数中，优先选择 URL 中指定的表单
- 如果 URL 中的 `formId` 在表单列表中不存在，则选择第一个表单

**代码位置**:
```typescript
// 从 URL 获取 formId
const [searchParams] = useSearchParams();
const urlFormId = searchParams.get('formId');

// 初始化状态
const [selectedFormId, setSelectedFormId] = useState<string>(urlFormId || '');

// 获取表单列表时，优先选择 URL 中指定的表单
const fetchFormList = async () => {
  try {
    const result = await formApi.getAll();
    setFormList(result || []);
    
    // 如果 URL 中有 formId，优先选择该表单
    if (urlFormId && result && result.length > 0) {
      const targetForm = result.find((form: FormDefinition) => form.id === urlFormId);
      if (targetForm) {
        setSelectedFormId(urlFormId);
        return;
      }
    }
    
    // 如果没有选中表单，默认选择第一个
    if (result && result.length > 0 && !selectedFormId) {
      setSelectedFormId(result[0].id);
    }
  } catch (error) {
    console.error('获取表单列表失败:', error);
  }
};
```

### 4. 字段新增页面接收表单 ID

**文件**: `src/pages/FormMode/FieldManage/FieldAdd.tsx`

**实现方式**:
- 从 URL 参数中获取 `formId`（通过 `useSearchParams` hook）
- 在提交表单时，将 `formId` 传递给 `fieldApi.create()` 方法
- 提交成功后，返回字段管理列表页面，并传递表单 ID

**代码位置**:
```typescript
// 从 URL 获取 formId
const [searchParams] = useSearchParams();
const formId = searchParams.get('formId');

// 提交表单时使用 formId
const handleSubmit = async (values: FieldDefinitionFormData) => {
  if (!formId) {
    message.error('表单ID不能为空');
    return;
  }

  setLoading(true);
  try {
    await fieldApi.create({
      ...values,
      formId,
    });
    message.success('新增成功');
    // 返回字段管理列表，并传递表单ID
    navigate(`/formmode/fieldmanage?formId=${formId}`);
  } catch (error) {
    console.error('新增失败:', error);
    message.error('新增失败');
  } finally {
    setLoading(false);
  }
};
```

## 交互流程

### 流程一：新增表单后配置字段

1. 用户进入 **表单管理列表页面** (`/formmode/formmanage`)
2. 点击 **"新增"** 按钮，进入表单新增页面 (`/formmode/formmanage/aae?mode=add`)
3. 填写表单信息（表单名称、数据库表名等）
4. 点击 **"保存"** 按钮，提交表单
5. 表单创建成功后，显示确认对话框：
   - 点击 **"下一步：配置字段"** → 跳转到字段新增页面 (`/formmode/fieldmanage/aae?mode=add&formId=xxx`)
   - 点击 **"返回列表"** → 返回表单管理列表页面
6. 在字段新增页面，配置字段信息
7. 点击 **"保存"** 按钮，提交字段
8. 字段创建成功后，返回字段管理列表页面 (`/formmode/fieldmanage?formId=xxx`)

### 流程二：编辑表单后管理字段

1. 用户在 **表单管理列表页面** (`/formmode/formmanage`)，点击某个表单的 **"编辑"** 按钮
2. 进入表单编辑页面 (`/formmode/formmanage/aae?mode=edit&id=xxx`)
3. 修改表单信息
4. 可以点击 **"管理字段"** 按钮，跳转到字段管理列表页面 (`/formmode/fieldmanage?formId=xxx`)
5. 在字段管理列表页面，可以查看、新增、编辑、删除该表单的字段

## 技术要点

### 1. 数据传递

- 使用 **URL 参数** 传递表单 ID (`formId`)
- 在页面之间跳转时，通过 URL 参数保持数据状态
- 例如：`/formmode/fieldmanage/aae?mode=add&formId=123`

### 2. 状态管理

- 使用 `useState` 管理表单选择状态 (`selectedFormId`)
- 使用 `useEffect` 监听 `selectedFormId` 变化，自动加载字段列表
- 使用 `useSearchParams` 获取 URL 参数

### 3. 用户体验

- 表单创建成功后，提供明确的下一步操作指引
- 编辑表单时，可以快速跳转到字段管理页面
- 字段管理页面自动选择对应的表单，无需手动选择

## 权限配置（模块 / 字段 / 数据范围）

**入口**：表单管理列表操作列「权限」按钮（受 `formmanage_aae` 权限控制）→ 内嵌抽屉
**文件**：`src/pages/FormMode/FormManage/FormManage.tsx`（按钮+状态）、`src/pages/FormMode/FormRight/FormRightDrawer.tsx`（抽屉，3 Tab）

**后端**：`FormRightController`，路由前缀 `/api/blade-formmode/right/*`

### 三类权限（各自一张表、独立 get/save）

| 表 | Tab | 关键字段 | objtype 编码 |
|---|---|---|---|
| `moderightinfo` | 模块权限 | `righttype`：1可见 2新建 3编辑 4删除 5详情 6导入 7导出；`includesub` | 1角色 2部门 3岗位 4人员 |
| `modefieldauthorize` | 字段权限 | `rightvalue`：1可见 2可编辑；`fieldid`（workflow_billfield.id） | 1角色 2部门 3岗位 4人员 |
| `modedatasharerule` | 数据范围 | `type`：1查看 2维护；`includeSub`、`creatorSelf` | 1角色 2部门 3岗位 4人员（**已统一**） |

抽屉每 Tab 支持新增/删除行，一次「保存」提交三类（全量替换）；空 `objid` 行保存时过滤。

### formId → modeId 桥接
- 权限按 `modeId`（modeinfo.id）落库，但管理端停留在表单维度，故新增 `GET /right/resolve-mode/{formId}` 反查。
- 反查不到（表单未建模块）时：抽屉顶部告警并禁用编辑/保存。
- **跨 ID 体系兜底（2026-10-21）**：`modeinfo.billid` 存的是 ecology 迁移的小 billid（如 `5`），而表单列表的 `workflow_bill.id` 是雪花 ID（如 `2064530495200337922`），二者指向**同一张物理表**（`formtable_main_5`）。此前直连反查失败 → 真实表单在抽屉里显示「尚未创建模块」而不可用。现 `resolveModeIdByFormId` 增加两级兜底：
  1. 直连：`modeinfo.billid = formId`；
  2. 按物理表名：`formId → workflow_bill.tablename → 同表其它 bill 记录的 id 集合 → modeinfo.billid IN (...)`；
  3. 表名后缀推导：`formtable_main_5 → 5` 作为补充候选（覆盖 `workflow_bill` 中该 billid 记录已缺失的迁移数据）。
  实测：表单 `2064530495200337922` 与 `5` 均正确解析到模块 `2106000000000000001`。

### 数据范围表与实测结论（2026-10-21）
- **`modedatasharerule` 表此前在库中不存在**（Flyway 未在本模块启用，`V2026.10.20_004` 建表迁移从未执行），导致数据范围保存静默失败（`data:false`、回读为空）。现新增 `SchemaInitRunner`（dev/test 启动 `CREATE TABLE IF NOT EXISTS`，幂等、与迁移脚本不冲突）自愈建表；生产仍建议执行 `V2026.10.20_004`。
- **行级拦截实测（真实数据 140 行）**：引擎默认 `canViewAll=false` + `creatorId=当前用户`（fail-closed），仅命中规则才放行。
  - 列表/分页 `POST /form/data/page/{modeId}`：无规则 → `total=0`；存「命中当前部门」规则 → `total=140`；清空规则 → 回到 `0`。
  - 单条 `GET /form/data/by-form?formId=&dataId=`：无规则 → 「数据不存在」；命中规则 → 正常返回字段值；清空 → 再次「数据不存在」。
- **跨体系 creator 已被实证**：表内行的 `modedatacreator = -540541951`（ecology 负数 ID）≠ admin 雪花 userId，故无命中规则时 admin 看不到任何行——即「本人创建」在迁移数据上需 ID 映射才能按预期生效。

### objtype 编码统一（2026-10-20）
- **目标**：三表统一为 `1角色 2部门 3岗位 4人员`（此前 `modedatasharerule` 用 `1人员 2部门 3角色 4岗位`，同一数字含义相反）。
- **数据迁移**：`doc/sql/migration/V2026.10.20_005__form_mode_data_share_rule_objtype_unify.sql`
  映射：人员 `1→4`、部门 `2→2`、角色 `3→1`、岗位 `4→3`（CASE 同批计算，无中间态冲突）。
- **解析引擎**：`ModeDataShareRuleServiceImpl` 常量 `OBJ_ROLE=1 / OBJ_DEPT=2 / OBJ_JOB=3 / OBJ_PERSON=4`（`matchRule` 按名引用，匹配逻辑不变）；单测同步改值。
- **前端**：抽屉原两套下拉 `OBJTYPE_RF` / `OBJTYPE_SCOPE` 合并为单一 `OBJTYPE_OPTS`，三 Tab 共用。
- **⚠️ 上线约束**：迁移脚本与引擎代码须**同批部署**（先迁数据后按新值解释）；脚本**不可重复执行**——值域 `1..4` 在新旧方案下均占用，无法按值判重，依赖迁移框架按版本号仅应用一次。

### 已知限制（暂未扩大范围）
